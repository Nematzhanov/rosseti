# Прогнозирование электропотребления по федеральным округам России методами машинного обучения с учётом погоды — план исследования

## 0. Что уже собрано

| Набор | Где | Что внутри |
|---|---|---|
| Потребление и генерация, почасово, 8 энергосистем (ЕЭС + 7 ОЭС), 28.09.2025–27.09.2026 | `all_energy_systems_hourly_*.csv`, `wide_hourly_*.csv`, `by_energy_system/` | `generation_mw`, `consumption_mw`, время МСК. Источник: [СО ЕЭС, «Генерация (час)»](https://www.so-ups.ru/functioning/ees/ees-indicators/ees-gen-consump-hour/) |
| Погода Северо-Запада, почасово, 10 точек + средневзвешенная по ОЭС | `weather/` | 3 варианта: `actual` (факт, ERA5), `hist_fcst` (архив прогнозов), `dayahead` (прогноз, выпущенный за сутки). Источник: Open-Meteo |

Скрипты: `download.py` (СО ЕЭС, докачивает недостающее), `weather/download_weather.py` (погода).

Важные детали данных:
- На сайте СО ЕЭС показан только ряд генерации, но в HTML лежит и ряд потребления (`data-datay`) — его мы и берём как целевую переменную.
- Это **оперативные** данные; уточнённые помесячные цифры СО ЕЭС публикует в пресс-релизах. Разница генерации и потребления — сальдо перетоков.
- Сайт отвечает 503 на частые запросы — качать не быстрее одного запроса в 2 секунды.

## 1. Постановка задачи

**Цель:** почасовой прогноз потребления на сутки вперёд (24 значения) для каждой энергосистемы; дополнительно — на неделю вперёд.

**Ключевая оговорка: СО ЕЭС публикует данные по ОЭС, а не по федеральным округам.** Границы близки, но не совпадают:

| ОЭС | Примерное соответствие федеральным округам |
|---|---|
| ОЭС Северо-Запада | СЗФО без Вологодской обл. (она в ОЭС Центра) и без изолированного НАО |
| ОЭС Центра | ЦФО + Вологодская обл. |
| ОЭС Юга | ЮФО + СКФО |
| ОЭС Средней Волги | часть ПФО (Татарстан, Самарская, Саратовская, Нижегородская, Ульяновская, Пензенская, Чувашия, Мордовия, Марий Эл) |
| ОЭС Урала | УФО + часть ПФО (Башкортостан, Пермский край, Удмуртия, Оренбургская, Кировская) |
| ОЭС Сибири | СФО + Бурятия и Забайкальский край (ДФО) |
| ОЭС Востока | юг ДФО (Приморье, Хабаровский край, Амурская обл., ЕАО, Якутия частично); изолированные системы ДФО не входят |

Состав надо сверить с [Отчётом о функционировании ЕЭС в 2025 году](https://www.so-ups.ru/fileadmin/files/company/reports/disclosure/2026/ups_rep2025.pdf).

Варианты для темы «по федеральным округам»:
1. **(рекомендую)** Работать на уровне ОЭС как приближения ФО и явно описать соответствие в работе.
2. Разложить ОЭС на ФО по годовым долям субъектов (отчёт СО ЕЭС, [Росстат](https://rosstat.gov.ru/free_doc/new_site/business/prom/el_potr.htm)) — грубо, потому что почасовых данных по субъектам в открытом доступе нет.

**Пилот — ОЭС Северо-Запада**, затем та же схема для остальных ОЭС.

## 2. Данные

### 2.1 Целевая переменная
- Уже есть 1 год. **Одного года мало**: годовая сезонность видна один раз, и валидировать зиму не на чем. Нужно докачать 3–5 лет (`python3 download.py --start 2021-01-01`), сначала проверив, с какой даты сайт отдаёт данные.
- Проверить пропуски, выбросы, аварии и нулевые часы.

### 2.2 Погода
Почему три варианта погоды: если обучать и проверять модель на **фактической** погоде, оценка точности будет завышена — в реальности на завтра известен только **прогноз** погоды. Честная схема:
- обучение — на `hist_fcst` или `actual`;
- тест — **обязательно** на `dayahead` (прогноз за сутки);
- в работе показать разницу «факт vs прогноз погоды» как отдельный результат.

Ошибка прогноза температуры на сутки вперёд по Северо-Западу за год — **~1,1 °C MAE** (посчитано на скачанных данных).

Точки для Северо-Запада: Санкт-Петербург, Ленинградская обл. (Гатчина), Петрозаводск, Мурманск, Архангельск, Сыктывкар, Великий Новгород, Псков, Калининград; Вологда — отдельно, как часть СЗФО из ОЭС Центра. Средневзвешенная температура сейчас считается по населению; лучше заменить веса на годовое потребление субъектов (из отчёта СО ЕЭС).

Для остальных ОЭС — добавить точки в `POINTS` в `download_weather.py` (по 1–3 крупных города на субъект).

Архив прогнозов (`previous-runs`) в Open-Meteo доступен примерно с 2024 г., поэтому при удлинении истории до 3–5 лет ранние годы придётся брать с фактической погодой.

Альтернативные и проверочные источники:
- [СО ЕЭС, «Температура»](https://www.so-ups.ru/functioning/ups/indicators/ees-temperature/) — собственная температура оператора по ОЭС; сверить с нашей средневзвешенной.
- rp5.ru — наблюдения станций Росгидромета (ручная выгрузка).
- Meteostat (Python-библиотека), ERA5 напрямую из Copernicus CDS.

### 2.3 Календарь
- Производственный календарь РФ: праздники, переносы выходных, предпраздничные дни (пакет `holidays` для RU или API isdayoff.ru).
- Долгота светового дня (освещение) — есть в Open-Meteo daily (`daylight_duration`).

## 3. Признаки

- **Лаги потребления**, доступные на момент прогноза: t−48, t−72, t−168 (на сутки вперёд лаг t−24 для части часов ещё неизвестен — учесть время выпуска прогноза).
- Скользящие средние и «тот же час неделю назад».
- **Погода:** средневзвешенная температура, градусо-часы отопления (HDD, база 15–18 °C), экспоненциально сглаженная температура за 24–72 ч (тепловая инерция зданий), ветер (охлаждение), облачность и радиация (освещение), глубина снега.
- **Календарь:** час, день недели, месяц (циклическое кодирование sin/cos), флаги праздников и переносов.
- Для общей модели по всем ОЭС — идентификатор ОЭС как статический признак.

## 4. Модели

### 4.1 Базовые (обязательно для сравнения)
- Сезонный наивный прогноз: тот же час неделю назад.
- Линейная регрессия на HDD + календарь.
- **Прогноз самого СО ЕЭС** — в `graph.js` сайта есть тип графика «План генерации и потребления»; найти страницу и скачать план потребления. Это лучший эталон: если модель точнее или сопоставима с планом оператора, это сильный результат.

### 4.2 Классическое машинное обучение
- **LightGBM / CatBoost** — сильный и быстрый бейзлайн для краткосрочного прогноза нагрузки, объяснимость через SHAP.

### 4.3 Нейросети, обучаемые с нуля
- N-HiTS, NBEATSx, TFT, TiDE (библиотеки NeuralForecast или Darts) — поддерживают внешние признаки. В свежем бенчмарке по нагрузке системного оператора обычный Transformer, обученный с нуля, обошёл остальные методы ([arXiv 2607.15705](https://arxiv.org/html/2607.15705v1)).

### 4.4 Предобученные модели («ИИ, который можно дообучить»)

| Модель | Размер | Лицензия | Погода как признак | Дообучение | Вывод |
|---|---|---|---|---|---|
| **[Chronos-2](https://github.com/amazon-science/chronos-forecasting)** (Amazon) | 120M (есть small 28M) | Apache-2.0 | да, прошлые и будущие ковариаты | да: LoRA и полное; в AutoGluon — `fine_tune=True` | **Основной кандидат.** Первое место на GIFT-Eval |
| **[Granite TTM-R3](https://huggingface.co/ibm-granite/granite-timeseries-ttm-r3)** (IBM) | 1–35M | проверить в карточке модели | да, exogenous infusion + channel mixing | да, полное дообучение (рекомендуется для неё) | **Второй кандидат**: дообучается за минуты на CPU/ноутбуке |
| **[TiRex-2](https://huggingface.co/NX-AI/TiRex-2)** (NX-AI, июль 2026) | ~40M | Apache-2.0 | да, прошлые и будущие ковариаты | **нет** в открытой версии (только Pro) | Сравнение в режиме zero-shot |
| TimesFM 2.5 (Google) | 200M | Apache-2.0 | через обёртку XReg | возможно | Запасной вариант |
| Moirai 2.0 (Salesforce) | — | проверить (у весов Moirai были некоммерческие ограничения) | слабо использует погоду ([arXiv 2602.05390](https://arxiv.org/html/2602.05390)) | да (uni2ts) | Не рекомендую |
| TimeGPT (Nixtla) | — | закрытая, только API | да | через API | Не рекомендую: данные уходят во внешний сервис |

Что известно из свежих работ (2026):
- Без дообучения Chronos-2 проигрывает специализированным моделям на нагрузке энергосистем; **полное дообучение** снизило MAPE с 6,71 % до 4,06 % на данных ISO New England с погодой ([arXiv 2609.06656](https://arxiv.org/html/2609.06656)).
- В другой работе для Chronos-2 лучше сработала LoRA, а полное дообучение переобучалось ([arXiv 2607.23146](https://arxiv.org/html/2607.23146)). Вывод: **сравнить оба варианта**; при 1 годе данных риск переобучения высокий — ещё один довод докачать 3–5 лет.
- Погода помогает сильнее всего в климате с большими перепадами температур — это как раз наш случай. Лучше всего её используют модели с явным смешиванием каналов: Chronos-2 и TTM ([arXiv 2602.05390](https://arxiv.org/html/2602.05390)).

Железо: TTM и LightGBM — ноутбук; Chronos-2 с LoRA — Apple Silicon (MPS) или бесплатный GPU в Colab.

## 5. Эксперименты и оценка

- **Разбиение по времени**, без перемешивания: rolling-origin backtest (расширяющееся окно). Тест — последние 2–3 месяца; при нескольких годах — отдельно зима и лето.
- **Метрики:** MAPE, MAE (МВт), RMSE; отдельно — ошибка в часы пика; для вероятностных прогнозов — pinball loss / WQL.
- **Абляции** (обязательная часть работы):
  1. без погоды / фактическая погода / прогноз погоды;
  2. одна точка (Санкт-Петербург) / средневзвешенная / все точки как отдельные признаки;
  3. Chronos-2: zero-shot / LoRA / полное дообучение; TTM: zero-shot / дообучение;
  4. отдельная модель на каждую ОЭС / одна общая модель на все ОЭС.

## 6. Этапы

| Неделя | Работа |
|---|---|
| 1 | Докачать 3–5 лет СО ЕЭС; найти и скачать план потребления СО ЕЭС; разведочный анализ (сезонность, зависимость от температуры, праздники) |
| 2 | Признаки, календарь; погода для остальных ОЭС |
| 3 | Бейзлайны + LightGBM/CatBoost для ОЭС Северо-Запада |
| 4–5 | Chronos-2 и TTM: zero-shot → дообучение; TiRex-2 zero-shot |
| 6 | Абляции по погоде, сравнение с планом СО ЕЭС |
| 7 | Масштабирование на все ОЭС (приближение ФО) |
| 8 | Выводы, текст, графики |

## 7. Риски

- **ОЭС ≠ ФО** — описать в работе явно (раздел 1).
- **Короткая история** — 1 год недостаточен для дообучения больших моделей и оценки зимы.
- Оперативные данные уточняются задним числом.
- **Калининград:** с февраля 2025 г. энергосистема работает изолированно от стран Балтии; проверить, входит ли она в цифры ОЭС Северо-Запада.
- Структурные сдвиги: новые крупные потребители, сезонные запреты майнинга в ряде регионов Сибири, выход и ввод крупных промышленных нагрузок.
- Утечка будущего: признаки должны быть доступны на момент выпуска прогноза (лаги, погода — только прогнозная на тесте).
